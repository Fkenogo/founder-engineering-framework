## 1. Purpose

This guide provides the criteria and process for evaluating Framework Evolution submissions. It ensures that evaluation is consistent, evidence-based, and proportionate.

## 2. Evaluation Criteria

Each submission shall be evaluated against the following criteria:

| Criterion               | Question                                                                                | Evidence Required                                                    |
| ----------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Evidence quality        | Is the lesson grounded in observable engineering practice?                              | Attributable project records, decisions, or operational observations |
| Commonality             | Is the problem likely to recur across multiple Founder projects?                        | Comparison with existing FEF domains and project patterns            |
| Non-project-specificity | Is the lesson independent of product architecture, technology stack, or delivery model? | Assessment of applicability to other project types                   |
| Governance relevance    | Does the lesson relate to engineering governance rather than product design?            | Classification against FEF governance boundaries                     |
| Proportionality         | Does the benefit of framework adoption exceed the cost?                                 | Cost-benefit assessment of implementation effort vs recurring value  |
| Stability               | Does the lesson avoid destabilising existing approved governance?                       | Compatibility check with D1–D4 outputs and DG-1–DG-6 lifecycle       |

## 3. Commonality Assessment

The evaluator shall determine whether the lesson is:

| Classification      | Test                                                                                                     |
| ------------------- | -------------------------------------------------------------------------------------------------------- |
| Project-specific    | Applies only to the source project or a narrow class of projects                                         |
| Common pattern      | Recurs across multiple project types but does not require framework change                               |
| Framework candidate | Addresses a systemic governance gap that affects multiple projects and cannot be solved at project level |

## 4. Stability Assessment

The evaluator shall confirm that the submission:

- does not contradict D1–D4 outputs;
- does not require amendment of approved governance instruments;
- does not introduce new lifecycle stages;
- does not create register overlap;
- does not blur the boundary between common FEF governance and project engineering governance.

## 5. Adoption Recommendation Categories

| Category            | Meaning                                                                      |
| ------------------- | ---------------------------------------------------------------------------- |
| Project-specific    | The lesson should be adopted by the source project only; no framework action |
| Monitor             | The lesson should be observed for recurrence before framework consideration  |
| Framework candidate | The lesson should be recommended to the Founder for prioritisation           |
| No action           | The lesson does not warrant adoption or further observation                  |

## 6. Decision Outcomes

| Outcome                        | Authority                        | Effect                                                 |
| ------------------------------ | -------------------------------- | ------------------------------------------------------ |
| Submitted for Review           | Intake Coordinator               | Registered in Candidate Register                       |
| Recommended for Prioritisation | Evaluator                        | Presented to Founder for selection                     |
| Prioritised for Evolution      | Founder                          | Authorised for future Framework Evolution work package |
| Implemented                    | Framework Evolution work package | Incorporated into framework                            |
| Closed                         | Intake Coordinator               | Preserved as evidence; no further action               |

## 7. Non-Effects

This review guide:

- does not amend constitutional documents;
- does not modify D1–D4 outputs;
- does not commence D5 or D6;
- does not perform Framework Evolution;
- does not approve or reject submitted candidates;
- does not create additional governance domains;
- does not introduce unnecessary lifecycle stages.
