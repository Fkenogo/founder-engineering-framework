## 1. Purpose

This standard defines the required structure, evidence expectations, cross-project applicability criteria, and lifecycle for Framework Evolution submissions. It ensures that engineering lessons are preserved in a form that enables controlled evaluation and prioritisation.

## 2. Required Submission Structure

Every Framework Evolution submission shall contain the following sections:

| Section                      | Required Content                                                                |
| ---------------------------- | ------------------------------------------------------------------------------- |
| Submission identifier        | Unique identifier allocated by the submitter                                    |
| Title                        | Concise descriptive title                                                       |
| Source project               | Originating Founder project identifier                                          |
| Date                         | Submission date                                                                 |
| Submitter                    | Attributable individual or role                                                 |
| Executive summary            | One-paragraph summary of the lesson                                             |
| Problem statement            | What engineering problem or friction was observed                               |
| Observed practice            | What practice was actually followed                                             |
| Evidence                     | Supporting evidence, references, or artefacts                                   |
| Cross-project applicability  | Assessment of whether the lesson applies beyond the source project              |
| Proposed framework relevance | Whether the lesson suggests a framework-wide improvement                        |
| Recommendation               | Submitter's recommendation (Project-specific / Framework candidate / No action) |
| Non-effects                  | What the submission does not propose to change                                  |

## 3. Evidence Expectations

Submissions must include evidence that is:

- **Attributable** — traceable to a specific project, decision, or practice;
- **Observable** — based on actual engineering activity, not speculation;
- **Preserved** — not amended after submission;
- **Bounded** — limited to the lesson's scope, not a general critique.

Acceptable evidence forms include:

- Project decision records;
- Repository artefacts;
- Validation reports;
- Session records;
- Closure reports;
- Programme checkpoints;
- Operational observations with dates and context.

## 4. Cross-Project Applicability Criteria

A lesson shall be classified as a **Framework Evolution Candidate** only if it satisfies all of the following:

| Criterion            | Test                                                                                                  |
| -------------------- | ----------------------------------------------------------------------------------------------------- |
| Commonality          | The lesson addresses a problem that is likely to recur across multiple Founder projects               |
| Non-project-specific | The lesson is not dependent on a particular product architecture, technology stack, or delivery model |
| Governance relevance | The lesson relates to engineering governance, not product design or marketing                         |
| Proportionality      | The cost of adopting the lesson into the framework does not exceed the benefit                        |
| Stability            | The lesson does not destabilise existing approved governance                                          |

## 5. Submission Lifecycle

| Stage | State        | Description                                                                  |
| ----- | ------------ | ---------------------------------------------------------------------------- |
| 1     | Submitted    | Received and registered in the Framework Evolution Candidate Register        |
| 2     | Under Review | Evaluated against the Framework Evolution Review Guide                       |
| 3     | Recommended  | Recommended for Founder prioritisation                                       |
| 4     | Prioritised  | Selected by the Founder for future Framework Evolution                       |
| 5     | Implemented  | Incorporated into the framework through a separately authorised work package |
| 6     | Closed       | No further action; preserved as evidence                                     |

A submission may also be classified as **Project-specific** at any stage if it does not satisfy the cross-project applicability criteria.

## 6. Non-Effects

This submission standard:

- does not amend constitutional documents;
- does not modify D1–D4 outputs;
- does not commence D5 or D6;
- does not perform Framework Evolution;
- does not approve or reject submitted candidates;
- does not create additional governance domains;
- does not introduce unnecessary lifecycle stages.
